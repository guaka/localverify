# Localization plan

Status: proposed; this document does not indicate shipped language support.

Use **L10N** (localization) for this plan: the goal is to ship and maintain more
languages. **I18N** (internationalization) is the engineering foundation that makes
that possible, covered in the first phases below.

## Initial languages

English remains the source language and fallback. The proposed first set is
`en, zh-Hans, hi, es, fr, ar, pt-BR, ru, id` across iOS and Android.

| Tag | Language | Initial scope / decision |
| --- | --- | --- |
| `en` | English | Complete, reviewed source copy and fallback. |
| `zh-Hans` | Simplified Chinese | Explicit script; Traditional Chinese is outside this rollout. |
| `hi` | Hindi | Verify Devanagari shaping, wrapping, and accessible reading. |
| `es` | Spanish | Broadly understandable wording; regional variants can follow. |
| `fr` | French | Broadly understandable wording; check expansion and punctuation. |
| `ar` | Arabic | Modern Standard Arabic; full right-to-left support. |
| `pt-BR` | Brazilian Portuguese | Initial Portuguese locale; European Portuguese (`pt-PT`) can follow separately. |
| `ru` | Russian | Review plural forms and longer technical labels. |
| `id` | Indonesian | Use `id` as the canonical language tag; verify platform resource mapping. |

These are language targets, not a ranking by audience size. Release order should
follow reviewer availability and validation, without implying support for an
unreviewed locale. Language choice must not determine a user's region, time zone,
or evidence format.

## Current baseline

- iOS text lives largely in `iOS/App/LocalVerifyApp.swift`,
  `iOS/App/CollectionGuide.swift`, and `iOS/Share/ShareViewController.swift`.
  There are no string catalogs yet. `tools/generate_project.py` declares only
  `en` and `Base` as known regions.
- Android text needs extraction from the Compose UI and core presentation paths.
  `Android/app/src/main/res/values/strings.xml` currently contains only the app
  name. The manifest already declares RTL support, which still needs UI validation.
- Swift and Kotlin core code also produce human-readable findings, errors, and
  exports. Translating visible labels alone will not cover the whole workflow.
- The [report contract](REPORT.md) and existing stored cases must remain compatible.

## Phase 0 — Scope and source copy

- Inventory app-owned text: navigation, collection guides, import/share flows,
  progress, cancellation, incomplete results, findings, coverage, errors, empty
  states, deletion, copy/export notices, accessibility labels, and About/privacy.
- Separate display text from technical identifiers and evidence. Record where
  each message originates and whether it is persisted or exported.
- Review English before translation. Create a glossary for “lead,” “match,”
  “indicator,” “coverage,” “incomplete,” and “no matches.” Preserve the distinction
  between a lead and proof of compromise; never translate “no matches” as “safe.”
- Give translators context, synthetic screenshots, placeholder descriptions,
  and the platform-specific collection steps. Use Brazilian Portuguese (`pt-BR`)
  and identify a fluent reviewer for each language.
- Scope the first release to the complete in-app workflow on both platforms.
  Keep exported reports in their existing English form initially and explain
  that limitation in localized export UI. Repository docs and distribution copy
  can follow separately; retain original licenses and third-party notices.

Exit: agreed inventory, glossary, locale policy, and explicit release scope.

## Phase 1 — Internationalization foundation

- Add iOS string catalogs for the app and share extension. Update the project
  generator so catalogs, resources, and supported regions survive regeneration
  in both standard and Files-only builds. Decide resource ownership explicitly
  for any strings rendered from the Swift package.
- Extract Android UI text into string/plural resources and use resource-backed
  Compose accessors. Keep a complete English default resource set; configure
  supported locales and platform language selection. Map script-specific tags
  correctly, including `zh-Hans` to `values-b+zh+Hans`.
- Follow system language preferences and platform per-app settings where
  available. Test fallback on unsupported languages and Android 11–12 as well
  as newer versions. Bundle translations for offline use.
- Use stable semantic keys with translator comments. Translate whole messages
  with typed placeholders, not concatenated fragments; use native plural rules.
  Separate internal state/filter values from translated labels.
- Format display dates, numbers, counts, and sizes using locale-aware APIs.
  Preserve machine-readable timestamps, identifiers, and report values.
- Keep core status/error codes and structured arguments separate from localized
  presentation. Where existing cases store English prose, preserve it as legacy
  detail and provide localized surrounding UI; do not rewrite stored evidence or
  attempt to translate arbitrary diagnostic text.
- Use flexible layouts and leading/trailing alignment. Audit directional icons,
  reading order, Dynamic Type/font scaling, VoiceOver, and TalkBack. Follow
  [Apple’s Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/right-to-left)
  for RTL behavior and
  [Android’s language and culture guidance](https://developer.android.com/training/basics/supporting-devices/languages).

Exit: English behavior remains intact, pseudo-localized expansion and RTL smoke
tests pass, and changing language does not change analysis or stored reports.

## Phase 2 — Pilot the translation workflow

- Pilot Spanish for a complete workflow, plus representative Arabic and
  Simplified Chinese screens to uncover direction and script issues early.
  Arabic/Chinese samples are internal validation, not advertised support.
- Include collection guidance, privacy warnings, incomplete/no-match results,
  and export controls in the pilot rather than testing navigation alone.
- Have a fluent reviewer approve terminology in context. Translation tools may
  assist with drafts; unreviewed drafts are not release-ready.
- Validate mixed-direction Arabic screens containing paths, URLs, hashes, dates,
  and Latin campaign names. Apply direction isolation only in presentation;
  copying must preserve the original technical value exactly.
- Establish checks for missing/stale keys, placeholder mismatches, required
  plural variants, and accidentally hard-coded app-owned UI text.

Exit: Spanish passes the per-language gate below; Arabic and Chinese pilot
findings are resolved or captured as blocking work for their release.

## Phase 3 — Complete the initial language set

- Suggested batches after the pilot: French, Brazilian Portuguese, and Indonesian;
  then Simplified Chinese, Hindi, Russian, and Arabic. Reorder for reviewer
  availability. RTL engineering starts in Phase 1, even if Arabic ships later.
- Translate the full inventory for each language, including accessibility copy
  and platform-specific collection instructions. Verify actual localized OS
  setting names; do not assume iOS and Android instructions are interchangeable.
- Track iOS and Android approval independently in each release checklist.
  Declare support only for languages that pass on that platform.

Exit: all nine languages, including English, meet the release gate on both apps.

## Phase 4 — Reports and ongoing maintenance

- Localize app-owned HTML report headings and explanatory copy after the UI
  rollout. Specify language selection and fallback before implementation; include
  an HTML language tag and direction, and make the selected report language clear.
- Keep JSON keys, enum values, ISO-8601 dates, hashes, rule IDs, indicator values,
  source paths, excerpts, and original filenames stable. Review any new metadata
  or structured message fields as a report-contract change with compatibility
  tests. Do not silently translate existing JSON prose fields.
- Preserve original evidence verbatim in every language. Apply RTL isolation and
  HTML escaping at render time without altering stored or copied content.
- Require source-copy changes to flag affected translations for review. Maintain
  the glossary and per-language reviewer status; recheck critical warnings before
  each release. Use English fallback for missing text, but block a locale's
  release on untranslated app-owned text in the agreed scope.
- Consider regional variants and translated user documentation after the initial
  set is sustainable. Use voluntary feedback, without adding telemetry.

## Per-language release gate

- All app-owned strings in scope are translated and reviewed, with explicit
  exceptions for product names, original legal notices, evidence, and legacy
  technical details. No missing keys, broken placeholders, or invalid plurals.
- A fluent reviewer approves the collection steps, findings terminology, privacy
  statements, and incomplete/no-match warnings in context.
- Synthetic end-to-end checks cover import/share, progress/interruption, findings,
  no matches, errors, copy, export, and deletion. Verify the iOS share extension
  and Files-only build as well as Android.
- Small-screen and large-text checks show no clipped actions or unreadable text;
  screen-reader order and labels work. Arabic passes native-language RTL review,
  and Hindi/Chinese pass script rendering checks.
- Language switching, unsupported-language fallback, and offline operation work.
  The same fixture yields identical analysis results and canonical evidence
  values regardless of display language.
- Localization QA uses generated synthetic fixtures only. Never copy actual
  sysdiagnose archives, extracted evidence, app containers, or case exports from
  a user's phone to the Mac for review. Keep evidence on the phone; any exception
  requires explicit permission. Never send real evidence to translation services.

and [Android locale resolution](https://developer.android.com/guide/topics/resources/multilingual-support).
